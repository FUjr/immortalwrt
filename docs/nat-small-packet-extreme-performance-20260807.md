# Misectel 7621EVB NAT 小包极限性能测试报告

测试日期：2026-08-07 UTC

## 1. 测试目的

本次测试用于评估 Misectel 7621EVB 在 VRF 1:1 NAT 场景下转发 64 字节
UDP 小包的能力，并比较默认 MAC 策略与较大规模 MAC 安全策略对性能的
影响。测试主要关注以下指标：

- 15Kpps 基本指标是否满足；
- 零丢包或接近零丢包时可持续的小包转发能力；
- 进入拥塞区后的最高实际交付 pps；
- 增加 MAC 允许列表和 IP-MAC 防欺骗规则后的性能变化。

## 2. 测试环境

### 2.1 被测设备

| 项目 | 内容 |
| --- | --- |
| 型号 | Misectel 7621EVB NAT Gateway |
| SoC | MediaTek MT7621 |
| 内核 | Linux 6.12.85 |
| 固件 | ImmortalWrt 25.12-SNAPSHOT `r0+37877-52c94e7647` |
| LAN 测试端口 | LAN2，100 Mbps Full Duplex |
| Flow offload | 软件和硬件 flow offload 均关闭 |

### 2.2 测试拓扑

```text
WAN 测试主机                           Misectel 7621EVB                    LAN 测试端
enp6s18                               WAN -> VRF2/LAN2                    RTL8152
10.96.210.226/24  ->  10.96.210.251  1:1 NAT  192.168.10.101  ->  192.168.10.101/24
iperf3 client                                                            iperf3 server
```

- 网关管理地址为 `10.96.210.253/24`。
- 测试期间临时建立 `10.96.210.251 -> vrf2/192.168.10.101` 的 1:1 NAT。
- RTL8152 接口为 `enx00e04c360eeb`，MAC 为 `00:e0:4c:36:0e:eb`。
- RTL8152 被放入独立 Linux 网络命名空间，避免 WAN 客户端与 LAN 服务端
  共用本机协议栈而产生本地短路。

## 3. 测试方法

### 3.1 流量模型

WAN 测试主机运行 `iperf3` UDP 客户端，LAN 网络命名空间内运行独立的
`iperf3` 服务端。每个档位持续 10 秒，相邻测试会话间等待 2 秒。基本命令
如下：

```sh
iperf3 -c 10.96.210.251 -u -b <请求速率> -l 64 -t 10 --json
```

`-l 64` 表示 64 字节 UDP 应用负载，并不表示完整以太网帧长度为 64 字节。
实际线上还包含 UDP、IPv4、以太网、FCS、前导码和帧间隙等开销。因此，
本报告的 pps 口径为 64 字节 UDP 数据报交付率。

测试请求速率依次为：`7.75`、`15`、`20`、`22`、`24`、`26`、`28`、
`30`、`45`、`50`、`55`、`60`、`75` 和 `100 Mbps`。

### 3.2 统计口径

所有结果从 `iperf3 --json` 原始输出提取：

```text
实际发送 pps = sum_sent.bits_per_second / (64 * 8)
实际交付 pps = sum_received.bits_per_second / (64 * 8)
丢包率       = sum_received.lost_percent
```

性能判断以实际交付 pps 为准，不使用配置的请求带宽推算网关性能。测试脚本
还检查每份 JSON 的 `error` 字段，40 份原始 JSON 均无会话错误。

### 3.3 MAC 策略对照

执行两组相同物理路径和流量参数的测试：

1. 默认策略：LAN2 无允许 MAC 列表、无 IP-MAC 防欺骗绑定，guard 关闭。
2. 增强策略：LAN2 配置 64 条允许 MAC，`mac_limit=64`，配置 64 条启用的
   IP-MAC 防欺骗绑定，并启用 `guard_mode=enforce`。

增强策略中包含真实测试端的 IP/MAC，另外加入 63 条未使用的合法表项。
运行时共生成 256 条 bridge nftables IP/ARP 匹配规则。端口允许列表由监控
进程检查，IP-MAC 规则位于实际二层转发路径中。

完整阶梯测试各执行一轮。为降低拥塞区调度波动造成的误判，另在 26、30、
45 Mbps 三个关键档位分别执行三轮，并使用中位值比较。

| 28 | 53,431.64 | 2.2723% | 53,820.14 | 1.5557% |

单轮结果显示，默认和增强策略在 26 Mbps 及以下均无丢包。28 Mbps 开始
进入拥塞过渡区；请求速率继续增加后，丢包率明显上升，实际交付吞吐不再
随请求速率线性增加。

默认策略单轮最高交付值为 `86,101.46 pps`，但对应丢包率为 `1.7244%`。
该结果代表拥塞状态下的单次峰值，不能作为无损转发能力。

### 4.2 三轮关键档复测

| 请求速率 | 策略 | 交付 pps 中位值 | pps 范围 | 丢包率中位值 |
| ---: | --- | ---: | ---: | ---: |
| 26 Mbps | 默认 | 50,770.04 | 50,768.42-50,771.19 | 0% |
| 26 Mbps | 增强 | 50,767.37 | 50,756.75-50,767.83 | 0% |
| 30 Mbps | 默认 | 56,904.89 | 56,882.29-58,259.85 | 2.8586% |
| 30 Mbps | 增强 | 56,749.00 | 56,162.95-56,926.35 | 3.0239% |
| 45 Mbps | 默认 | 78,716.64 | 75,810.67-86,101.46 | 10.3149% |
| 45 Mbps | 增强 | 81,871.80 | 78,826.75-82,341.76 | 6.5656% |

26 Mbps 档位下，默认策略三轮均为零丢包。增强策略两轮零丢包，一轮丢包
`0.0187%`，中位丢包率仍为零。两组交付 pps 中位值相差约 `2.67 pps`，
属于测量噪声范围。

30 Mbps 档位两组交付 pps 中位值相差约 `155.89 pps`，约为 `0.27%`，未
观察到显著的策略性能回退。45 Mbps 已处于明显拥塞区，两组结果区间重叠，
且默认策略自身波动达到约 10.3Kpps，不能根据单轮峰值认定增强 MAC 策略
造成稳定下降或提升。

### 4.3 端口错误统计

测试结束时 LAN2 的硬件统计为：

- `TxDrop=0`；
- `RxDrop=0`；
- `TxCrcErr=0`；
- `RxCrcErr=0`；
- `RxIngressDrop=0`；
- `RxArlDrop=0`。

因此，拥塞档位中的 `iperf3` 丢包不能归因为物理层 CRC 错误。丢包更符合
100 Mbps 出口排队、软件处理和测试端调度共同作用下的拥塞表现。

## 5. 结论

1. 设备在默认和增强 MAC 策略下均稳定通过 `>=15Kpps` 指标。
2. 默认策略的三轮零丢包能力已验证到约 `50.77Kpps`。
3. 增强策略在约 `50.77Kpps` 下三轮中两轮零丢包、一轮仅丢
   `0.0187%`，未观察到明显的常规负载性能下降。
4. 从 28-30 Mbps 请求速率开始进入拥塞过渡区，不能再按请求速率推算
   实际转发能力。
5. 默认策略单轮最高实际交付为约 `86.10Kpps`，但存在 `1.72%` 丢包；
   拥塞区三轮数据波动较大，因此不将该数值定义为稳定性能上限。
6. 64 条允许 MAC、64 条 IP-MAC 绑定和 256 条 bridge 匹配规则未导致
   15Kpps 或约 50Kpps 档位出现可测量的持续性能回退。

## 6. 测试边界

- 本报告测试的是 64 字节 UDP 应用负载，不是 64 字节完整以太网帧。
- `iperf3`、主机调度、USB RTL8152 和 Fast Ethernet 端口均属于测试链路，
  结果不是只测 MT7621 NAT 代码路径的实验室级隔离数据。
- 若验收要求 RFC 2544 风格的 64 字节线速帧、严格零丢包上限和精确时延，
  应使用硬件流量发生器或独立的内核级发包/收包端，并执行更长时间、多轮
  二分搜索测试。
- 本次未启用软件或硬件 flow offload，结果符合当前软件转发交付边界。
